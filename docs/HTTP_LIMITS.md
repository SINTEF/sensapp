# HTTP Request and Query Limits

SensApp bounds HTTP work to keep one request from using excessive memory.

- `SENSAPP_HTTP_BODY_LIMIT` defaults to `64MiB`. It applies to `/publish`, InfluxDB write, Prometheus remote write, and Prometheus remote read. Requests over the limit return HTTP 413. The server buffers each accepted request body before parsing it.
- Gzip-compressed InfluxDB writes, Snappy-compressed Prometheus requests and LZ4-compressed Arrow IPC bodies (the Python SDK sends them) are also limited after decompression. An expanded body over the configured size is rejected with HTTP 400. For Arrow, the uncompressed sizes that the buffers declare are added up before anything is decompressed.
- A client has 75 s (`SENSAPP_HTTP_HEADER_READ_TIMEOUT_SECONDS`) to send the headers of a request, from the moment it connects: a connection that sends nothing is closed too. The same timer closes a connection that stays idle between two requests, which is why it is above the 60 s idle timeout of the common proxies. An instance holds at most 4,096 connections: a connection over the cap waits until another closes. Without them, clients that open connections and send nothing would hold sockets and memory until the instance runs out of file descriptors. SensApp speaks HTTP/1.1 only (no HTTP/2 over cleartext): hyper starts the timer of an HTTP/2-capable listener only after the first bytes, so 4,096 silent connections held every permit. The proxies in front speak HTTP/1.1 upstream.
- A CSV upload is held in memory as text cells, one string per cell, and then as samples. Measured on 11 November 2026 (release build), a 4.5 MB CSV of 200,000 rows peaked at 63 to 69 MB over the body, wide or long: about 15 times the body (22 times before the cells were moved instead of copied). Send large CSV files in parts, or use Arrow.
- `SENSAPP_HTTP_MAX_CONCURRENT_WRITES` defaults to `16`. At most that many write requests run at once; a write that finds no free slot is rejected at once with HTTP 503 and a jittered `Retry-After`, before its body is read. `0` disables the limit. See [CONFIGURATION.md](CONFIGURATION.md#backpressure).
- `GET /series/{uuid}` allows at most 100,000 samples. An explicit `limit` above that is rejected. Without `limit`, the server detects a larger result and asks the client to narrow the time range or use aggregation.
- `limit` on `GET /series/{uuid}` returns the **oldest** N samples of the window, in time order, and does not signal that more exist. Use `start`/`end` to page through a series.
- `simplify` runs on the rows read for the window, after bucketing when `step` is set and after `limit`. If that read holds more than 100,000 rows, the request is rejected with HTTP 400 rather than simplified from a truncated read. Add `step` and `aggregation`, or narrow `start`/`end`. The 100,000 cap applies to the rows simplify reads, not only to its output.
- Selector queries and Prometheus remote read allow at most 256 series and 100,000 samples total (a Prometheus remote read of a plain selector, or of a `*_over_time` function, with a `step` that fits it, counts one sample per step instead of the raw samples, see [DATAMODEL.md](DATAMODEL.md#prometheus-remote-read-and-its-hints)). A query over a limit returns a client error instead of a truncated result. Cross-series aggregations (`avg by (room) (temperature[24h])`) are computed by the database, which returns buckets and not raw samples, so they have their own limits: at most 10,000 series, and 100,000 buckets in total. Without a `step` a series makes one bucket, and a larger `step` makes fewer buckets, so it raises what a query can cover: 300 series over 24 hours at one sample a minute are 432,000 samples, and 300 buckets with a `step` of one day.
- The Prometheus remote write stores the samples of float series only. Exemplars, native histograms and metric metadata are dropped, and the request still gets a `204`, as Prometheus would retry or drop a request answered otherwise. `sensapp_prometheus_remote_write_dropped_total{part="exemplar|histogram|metadata"}` counts what was dropped. NaN samples are dropped too, see [DATAMODEL.md](DATAMODEL.md#non-finite-floats).
- `/prometheus/metrics?include_latest_samples=true` allows at most 10,000 matching series. Filter by `metric` or `selector` when needed.
- A PromQL query (`/api/v1/query`) or selector (`/series?selector=`, `/prometheus/metrics?selector=`) is at most 4,096 bytes long and nested at most 64 levels deep, or it gets HTTP 400. The parser is recursive: measured on the 2 MiB stack of a request in a debug build, 150 nested parentheses or 700 unary minus signs overflowed it, which aborts the whole process and not only the request. The nesting counts the open brackets (`(`, `[`, `{`) and the unary `+`/`-` within them. Quoted label values are not counted, so they may hold any character.
- `simplify` runs Douglas-Peucker with an explicit stack, not by recursion, so its depth does not grow with the number of points. The recursive version overflowed a request's stack on 100,000 points of a zigzag with decreasing amplitude, where every point is kept.
- The HTTP metrics (`sensapp_http_requests_total`, `sensapp_http_request_duration_seconds`) are labelled with the route, never with the raw path: a request without a route is counted under `path="unmatched"`, and the files of the web UI under `path="/ui/*"`. Methods other than GET, POST, PUT, DELETE, HEAD, OPTIONS and PATCH are counted as `OTHER`. Otherwise anyone could add label values, without a token, that stay in memory until the process restarts.

The 100,000 samples are the default of `SENSAPP_HTTP_MAX_QUERY_SAMPLES`, which applies to every limit above that counts samples or buckets: raise it on a machine with memory to spare, lower it to try the limit. The series limits (256 and 10,000) and the other query limits are fixed. Operators can also change the request body size with `SENSAPP_HTTP_BODY_LIMIT`.

## Timeouts

- `SENSAPP_HTTP_BODY_READ_TIMEOUT_SECONDS` (default 30 s) bounds the time a client takes to send the body of a write or of a Prometheus remote read. Over it, the request is answered with HTTP 503 and a `Retry-After`, and nothing is written (a 408 would be dropped by Prometheus, which only retries 429 and 5xx). A write takes its write slot before its body is read, so without this bound 16 slow clients could hold every slot of an instance for the whole write timeout. 30 s covers a full 64 MiB body at about 2.2 MB/s, and the recommended 20 MB requests at about 0.7 MB/s. Raise it for devices on slow links.
- `SENSAPP_HTTP_SERVER_TIMEOUT_SECONDS` (default 120 s) bounds the reads and every other request, `SENSAPP_HTTP_WRITE_TIMEOUT_SECONDS` (default 300 s) bounds `/publish`, the InfluxDB write and the Prometheus remote write, and the vacuum has its own (`SENSAPP_HTTP_MAINTENANCE_TIMEOUT_SECONDS`, 3600 s). A request over its timeout is answered with HTTP 504.
- **Why 300 s for writes.** The work of a write grows with its body, which `SENSAPP_HTTP_BODY_LIMIT` bounds at 64 MiB: about 650,000 samples of InfluxDB line protocol. Measured on 1 October 2026 with a 1.33 M-sample series (release build, one client, a laptop): 2.6 years of history written in 200,000-sample requests took about 4 s on SQLite, 17 s on PostgreSQL and 60 s on TimescaleDB, which creates a chunk per week of data it has never seen (22,000 samples/s). A full 64 MiB body is then about 30 s in the slowest case, and 30 s was the old limit for everything. 300 s leaves ten times that, and still ends a hung database.
- **Why 120 s for reads.** A read of raw samples is bounded (100,000 samples), but an aggregation (`step` and `aggregation`) scans the whole window, so its time grows with the series. Measured on the same 1.33 M-sample series, whole-history aggregations took 0.17 to 0.98 s (SQLite's `last` was the slowest, TimescaleDB's `1d avg` the fastest). Read time is roughly linear in the samples scanned, so 120 s covers about 100 million samples on the slowest query measured, and several times more on the others. 30 s covered a quarter of that. The limits of a proxy in front still apply (see below).
- **The write slot is held until the parse ends.** The body of a write is parsed on a blocking thread, which cannot be cancelled: a client that disconnects does not stop its parse. The slot of the request stays taken until the parse returns, so the 16 slots bound the parsing work and not only the requests still connected.
- **A write is stored batch by batch.** A request is cut in batches of `SENSAPP_BATCH_SIZE` samples (8,192 by default) and each batch is its own transaction. When a request times out or fails midway, the batches already written stay stored, and sending the whole request again stores them a second time unless `SENSAPP_DEDUPLICATE_ON_INGEST` is on (or the vacuum removes them afterwards). This is why a timeout is not a good way to find out that a request is too big.
- **Prefer requests of 100,000 to 200,000 samples** (about 20 MB of line protocol, a few seconds) to one huge request. A failure then costs one small request to repeat, and it stays well under the timeouts of what sits in front of SensApp: a load balancer or a reverse proxy has its own, often 60 s (the default of an AWS load balancer and of nginx), and its 504 comes before SensApp's.
